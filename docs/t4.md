# T4. Модель доставки и безопасность пайплайна

## Способы развёртывания

| Способ | Учётные данные | Объём прав | Последствия компрометации |
| --- | --- | --- | --- |
| Push в `gh-pages` токеном workflow | `GITHUB_TOKEN` с `contents: write` | Запись во **весь** репозиторий на время job | Можно изменить код в любой ветке, подменить сайт, добавить вредоносный workflow |
| `upload-pages-artifact` + `deploy-pages` | Короткоживущий OIDC-токен (`id-token: write`) и `pages: write` | Только публикация Pages этого репозитория | Можно подменить сайт до следующего деплоя; код репозитория не затронут |
| `rsync`/`scp` по SSH с deploy-ключом | Приватный SSH-ключ в секретах | Всё, что может пользователь на сервере (на Helios — весь аккаунт студента) | Чтение и удаление всех файлов пользователя, запуск команд на сервере |
| FTP / SFTP | Логин и пароль (FTP передаёт их открытым текстом) | Файлы пользователя на хостинге | Как у SSH; у FTP пароль ещё и перехватывается в сети |
| S3 API (Object Storage) | Статический ключ доступа (access key + secret) | Задаётся политикой: можно ограничить одним бакетом и только записью | При узкой политике — подмена сайта в бакете; при широкой — доступ ко всему облачному аккаунту |

Вывод: лучше всего права ограничены у официального `deploy-pages` — у него нет
долгоживущих секретов. Самый «широкий» вариант в этой работе — SSH на Helios: ключ даёт
доступ ко всему аккаунту. Чтобы уменьшить риск, для CI создан **отдельный** ключ (не
личный), а в `authorized_keys` он добавлен с опцией `restrict` — без проброса портов,
агента и терминала. Если ключ утечёт, его достаточно удалить из `authorized_keys`.

## Ответы на вопросы

### Почему секреты недоступны в workflow по `pull_request` из форка

Workflow для pull request запускается с кодом **из форка**, то есть с кодом, который
написал посторонний человек. Если бы секреты были доступны, он мог бы добавить в свой PR
шаг `echo $SECRET | curl ...` и получить ключи. Поэтому GitHub для таких запусков не
передаёт секреты и выдаёт `GITHUB_TOKEN` только на чтение. В нашем workflow деплой
для `pull_request` вообще не запускается — выполняется только сборка.

### Зачем фиксировать actions по SHA, а не по тегу

Тег в git можно перенести на другой коммит. Если автора action взломают, злоумышленник
передвинет `v4` на свой коммит — и все, кто пишет `uses: actions/checkout@v4`, при следующем
запуске получат его код. SHA коммита изменить нельзя: он однозначно указывает на
конкретное содержимое. В workflow этой работы все actions указаны по SHA, версия —
в комментарии:

```yaml
- uses: actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1
```

### Supply-chain-атака через action

Action — это чужой код, который выполняется в нашем job с нашими секретами и токеном.
Если action скомпрометирован (взломан автор, перехвачено имя, вредоносное обновление
зависимости), он может:

- отправить секреты (SSH-ключ, токены) на внешний сервер;
- изменить собранные файлы сайта перед публикацией: вставить скрипт-майнер, фишинговую
  форму или редирект.

Для сайта это означает, что пользователи увидят подменённые страницы с «нашего» адреса,
а по украденному ключу злоумышленник получит доступ к серверу. Защита: фиксировать
actions по SHA, давать workflow минимальные `permissions`, передавать секреты только в те
шаги, которым они нужны.

### Как настроить known_hosts, не отключая проверку ключа хоста {#known-hosts}

Неправильно — `StrictHostKeyChecking=no`: тогда SSH подключится к любому серверу,
в том числе к подменённому, и отдаст ему данные.

Правильно — один раз получить ключ сервера и сохранить его в секрет:

```bash
ssh-keyscan -p 2222 helios.cs.ifmo.ru
ssh-keygen -lf <(ssh-keyscan -p 2222 helios.cs.ifmo.ru 2>/dev/null)
```

Вторая команда показывает отпечаток. Его нужно сравнить с отпечатком, который SSH показал
при первом ручном входе (`SHA256:3n1x6Bq0hnfyxrWB/YeQQPaxUkE/GCX2vKKtl0nzGgM` для
ED25519). Если совпадает — строку из `ssh-keyscan` сохраняем в секрет `HELIOS_KNOWN_HOSTS`,
workflow записывает её в `~/.ssh/known_hosts`. Если ключ сервера сменится, деплой упадёт
с ошибкой `Host key verification failed` — это и есть нужное поведение.

## Проверка без внешних CDN {#no-cdn}

Тема Material по умолчанию подключает шрифты Roboto с Google Fonts. В `mkdocs.yml`
это отключено (`font: false`), используются системные шрифты. Иконки темы встроены
в HTML как SVG, поиск и JavaScript лежат на самом сайте. Формулы рисует MathJax,
который скачан в `docs/javascripts/tex-svg.js` (вариант с SVG-выводом — ему не нужны
файлы шрифтов) и подключён через `extra_javascript`, а не с CDN.

Замеры для главной страницы (HTML + CSS + JS темы; для шрифтов учтены Roboto и Roboto Mono
400/700, латиница и кириллица — то, что браузер реально загрузит на этой странице):

| Вариант | Внешних запросов | Вес страницы со всеми ресурсами |
| --- | --- | --- |
| Шрифты с Google Fonts (по умолчанию) | 5 (1 CSS + 4 файла woff2) | ≈ 423 КБ (266 КБ сайт + 42 КБ CSS + 115 КБ шрифтов) |
| `font: false` (как на сайте) | 0 | ≈ 266 КБ |
| Страница с формулой: + локальный MathJax (`tex-svg.js`) | 0 | ≈ 266 КБ + 2059 КБ ≈ 2,3 МБ |

Проверка: в DevTools включить блокировку домена `fonts.googleapis.com`
(Network → Block request domain) и обновить страницу — сайт отображается и работает
полностью.
